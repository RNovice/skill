# Career Report — 工作經歷文件產生器

一次執行產出兩份文件：

| 版本 | 檔名 | 用途 |
|---|---|---|
| 完整版 | `工作經歷整理_YYYYMMDD.md` | 自己保存、與媒合顧問內部討論 |
| 去識別化版 | `工作經歷整理_去識別化_YYYYMMDD.md` | 對外投遞、轉交潛在雇主 |

## 使用方式

```
/career-report                       # 產出到 ~/Desktop
/career-report --out ~/Documents     # 指定輸出目錄
/career-report 用英文輸出             # 額外指示（附加在撰寫規則之後）
/career-report 只寫最近三個月          # 額外指示
```

`--out` 之外的文字皆視為 `additional_prompt`，於產出前作為補充規則套用；與本文件格式衝突時以使用者指示為優先。

## 執行步驟

### Step 1：收集對話語料

工作目錄用本 session 的 scratchpad（若無則 `/tmp/career-report`）。

```bash
python3 ~/.claude/skills/career-report/scripts/collect_prompts.py --out <WORKDIR>
```

輸出 `overview.txt`（各專案期間／活躍天數／prompt 數）與 `prompts.txt`（依專案與日期分組、去重、已剔除疑似憑證的語料）。

先讀 `overview.txt` 掌握全貌，再依腳本印出的行號**分段讀取** `prompts.txt`。

### Step 2：收集客觀證據

```bash
python3 ~/.claude/skills/career-report/scripts/collect_evidence.py --out <WORKDIR>
```

輸出 `evidence.txt`：各 repo 的 commit 貢獻佔比與期間、變更行數、分支數、作者排行、程式碼規模、目錄結構、各 manifest 的完整依賴清單。

repo 自動從對話紀錄的工作目錄推導；若有遺漏可用 `--repo <path>` 補指定（可重複）。

### Step 3：確認身分歸屬

`evidence.txt` 開頭的「判定為本人的身分」是自動比對結果。**動筆前先核對作者排行**：若某個 email／name 不確定是否為同一人，向使用者確認，不要直接把 commit 數算進去。多台機器、公司帳號、個人帳號並存是常態。

### Step 4：閱讀語料並歸納

逐段讀完 `prompts.txt`，對每個專案歸納出：

- **期間與角色**（主要開發者／貢獻者／維護者／研究負責人）
- **專案背景**（為什麼要做、從什麼狀態到什麼狀態）
- **技術棧**——以 `evidence.txt` 的 manifest 為準，不要從 prompt 猜
- **功能模組**——依產品面向分組，不要逐條列 prompt
- **技術亮點**——效能、架構、遷移、CI/CD、安全等可展現深度的主題單獨成段
- **可量化數據**——commit 數與佔比、程式碼規模、migration 數、腳本數、功能數量

### Step 5：撰寫完整版

依「輸出文件結構」產出，存為 `<out>/工作經歷整理_YYYYMMDD.md`。

### Step 6：撰寫去識別化版

先建立**代稱對照表**（僅存在於本次工作記憶，不寫入任何檔案），再逐項替換，存為 `<out>/工作經歷整理_去識別化_YYYYMMDD.md`。規則見「去識別化規則」。

### Step 7：回報

告知兩份文件路徑、關鍵量化數據、以及「待補充事項」中需要使用者本人提供的項目。

## 撰寫原則

### 語言轉換

把工程指令改寫成職務行為描述，保留技術深度但去掉操作細節：

| 原始語料 | 產出寫法 |
|---|---|
| 「修復 cell 改值造成整表重渲染」 | 以 React Profiler 定位並消除整表重渲染，收斂至儲存格級更新 |
| 「幫我開 ci 的 lint typecheck 階段」 | 從零建立 CI pipeline，涵蓋靜態檢查與多層安全掃描 |
| 「遷移腳本欄位型別跑掉了」 | 逐項核對新舊系統語意差異並修正 N 項落差 |
| 「幫我看 log 找原因」 | 完成正式環境事故的根因定位與修復 |

### 不誇大

- prompt 只證明「要求 AI 做過什麼」，**不證明成果**。任何量化數字必須來自 `evidence.txt`，或來自原始碼／文件可數的實體（migration 檔數、腳本數、模組數）。
- 變更行數含 lock 與產生檔，寫入文件時要標註「僅供規模參考」，或改用 commit 數與現行程式碼行數。
- 找不到證據支撐的成果，寧可不寫。
- 不推斷職稱、到職日、團隊規模、客戶數——全部列入「待補充事項」。

### 期間的誠實處理

`history.jsonl` 的最早日期只是**工具開始留存紀錄的時間**，不等於到職日。文件開頭必須聲明涵蓋期間與此限制；若語料中有試用期報告、年度回顧等線索可推估到職日，寫成「推估」並要求以勞動契約為準。

### 絕不寫入的內容

即使語料中出現也一律排除：帳號、密碼、JWT／API token、客戶或同事的個人資料、正式站可識別的資料筆數以外的客戶內容。（收集腳本已先過濾一輪，但仍需人工把關。）

## 去識別化規則

去識別化的目的是**保護雇主身分**，同時完整保留技術能力的證據。技術棧、量化數據、功能範圍**一律原樣保留**，不得替換或注水。

| 類別 | 處理方式 |
|---|---|
| 雇主名稱 | 改為產業＋規模描述，如「B2B SaaS 軟體公司」 |
| 產品名稱 | 改為產品類型，如「企業協作平台」 |
| 程式碼庫／repo 代號 | 改為功能描述，如「跨產品線設計系統與共用元件庫」 |
| 內部服務代號 | 改為服務職能，如「內部 LLM 服務」「用量管理服務」 |
| 網域、環境變數名 | 全部刪除 |
| 角色／權限字串 | 改為通用描述，如「RBAC 主管與管理員判定」 |
| 第三方合作對象 | 改為服務類型，如「第三方電子發票服務」 |
| 內部文件檔名、本機路徑 | 改為泛稱，如「遷移 Runbook」「調校文件」 |
| 同事姓名、email | 全部刪除；必要時只寫人數 |
| 日期粒度 | 收斂到月（降低指紋），但保留期間長度與活躍天數 |
| 開源套件、雲端服務、業界工具 | **保留**（Next.js、NestJS、GCP、Playwright 等不具識別性） |

產出後**自行複查一遍**：搜尋雇主名、產品名、repo 名、網域關鍵字確認零殘留。

回報時要誠實說明：去識別化只能降低而非消除可識別性——技術棧＋團隊規模＋時間軸＋產業的組合，同業仍可能推得出來。若使用者需要更保守的版本，可再將極具特徵的數字改為區間表述。

## 輸出文件結構

兩份文件使用相同章節，方便對照：

```
# 工作經歷整理（[去識別化版本]）

> 文件性質：資料來源說明
> 涵蓋期間：YYYY-MM-DD ~ YYYY-MM-DD，及「不等於到職日」的聲明
> 資料可信度／去識別化說明

## 一、個人定位摘要
   職務定位、最具代表性的成果、職涯方向變化

## 二、技術棧總覽
   分類表格：前端框架／狀態管理／UI／後端／資料庫／雲端／CI-CD／測試／可觀測性／AI／其他

## 三、主要專案
   ### 專案 A｜<名稱>
   | 期間 | 角色 | 團隊 | 產出量 |   ← 表格
   專案背景（一段）
   #### 1. 核心產品功能
   #### 2. 技術亮點（效能／架構／遷移等，依專案性質調整）
   #### 3. DevOps 與品質治理
   （依投入程度排序，主力專案寫深，其餘依比例縮減）

## 四、其他工作內容
   表格：工作項目 / 期間 / 內容

## 五、可量化成果彙總
   表格：指標 / 數值

## 六、可直接用於履歷的條列成就
   6-10 條 bullet，每條 = 動作 + 技術 + 量化結果，可直接複製進履歷

## 七、待補充事項
   編號列出需本人確認的資訊：到職日、職稱、團隊規模、產品規模數據、
   對外揭露範圍、學歷語言證照、前一份工作經歷
```

## 注意事項

- **Read 工具單次上限約 25000 tokens**：`prompts.txt` 動輒數千行，務必以 ≤650 行為單位分段讀取，不要一次讀完。
- **git 一律走腳本**：本環境的 Bash 層有輸出過濾／截斷機制，直接在 shell 跑 `git log | wc -l` 會得到被截斷的錯誤數字。收集腳本以 `subprocess` 直接呼叫 git，請勿改用 shell pipeline 重算。
- 主力專案的語料可能佔九成以上，但**次要專案是技術廣度的證據**（不同語言、不同角色、研究型任務），不要因為量少就省略。
- 兩份文件章節必須一一對應，方便使用者比對哪些內容被改寫。
- 若對話紀錄不足（少於數百筆），先告知使用者可產出的內容有限，並建議補充其他來源（git repo、JIRA、績效文件）。
